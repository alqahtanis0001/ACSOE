## Done before the phase opened — lead, not assigned

**The orchestrator command reader is fixed.** It looked up `store.claim_pending_commands`, which
`StoreClient` has never had, so a daemon wired to the real store ignored every command ever
written — the kill switch was inert, and Phase 0 reported green anyway because only test doubles
implemented that shape. Now composed from the four methods the store actually has, entirely inside
`core/`. Two further breaks in the same path were found and fixed: `mark_command_consumed` was
called with the wrong signature, and `mark_close_all_consumed` did not exist either, so even a
*successful* liquidation left its row unconsumed for the startup replay to re-run on the next boot.
The startup re-application of claimed-but-unconsumed rows is now wired, and it had never existed.

`commands_round_trip` is registered for phase 2 and passes. It refuses every double: real
migration, real `StoreClient`, real `Orchestrator`. **C proves it can fail** as part of spec 33.

## Standing rules for this phase

- Write only inside your own paths. `core/`, `bootstrap.py`, `config/`, `feature-specs/`, and
  `context/*` except your own progress file are the lead's.
- Before reporting any task complete, run all four yourself:
  `pytest tests/ -q` · `mypy --strict src/` · `ruff check src/` · `python scripts/verify.py --phase 2`.
  Mid-phase the bar is **no FAIL**; PENDING is expected.
- **`toolchain_green` now runs in every phase**, so a red suite is a FAIL on the phase gate. It was
  Phase 0 only until the Phase 1 close, which let `--phase 1` report no failures over a red suite.
- **If `pytest` dies with exit 139 rather than failing**, that is the known intermittent native
  fault in the seed write path — see Known Risks. **Capture the full trace before re-running** and
  paste it into your build log even if the next run is green. If the trace does not match the seed
  write path, stop and escalate: it is then something new.
- Never guess at trading behaviour. Open question in your progress file, stop that unit, escalate.
- Write `context/progress/<agent>.md` and append to `docs/build-log/phase-2/<agent>.md` **as you
  work**, not at the end. Three IDE crashes in Phase 1 each took the code and the log at different
  moments, and only the entries already written survived.
- Teammates do not commit. **The lead commits at every task boundary, not at phase close.**
  Operator process change, 2026-09-09, after a third session ended mid-flight: a completed spec
  with its four checks green is a commit. The point is that a session which dies resumes from a
  green tree rather than from a half-applied migration — which is exactly what the third one left
  behind. **Tell the lead the moment a spec is green** so it can be committed; do not batch
  several specs and report them together.
- The lead still does not commit anything that fails `scripts/verify.py`. A red tree is not a
  boundary, it is work in progress.
